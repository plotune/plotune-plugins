# Continuous requirement decomposition and approval separation

This workflow applies **inside an existing active project**, including while another workstream is implementing an earlier approved/frozen revision. It is not a mandatory new gate, fixed-level hierarchy, or a requirement to obtain user approval before writing every Draft. Compose `workspace-management`, `requirements-governance`, `work-orchestration`, `change-impact` and project-specific Guide / safety policy.

## When to derive a child proactively

During engineering delivery, review, architecture or verification, inspect the current applicable **parent ID plus exact revision**, real system boundary, interfaces, tests, unresolved decisions, sibling requirements and existing child requirements. When a distinct verifiable obligation necessary to satisfy a parent is not represented, derive it **as a new Draft rev 1** within the already authorized **writable project scope**. Do not wait for a user approval batch just to document an actionable Draft. Do not silently expand an expressly read-only analysis, a delegated scope without Draft-write authority, or an inaccessible workspace; provide a reviewable unsaved proposal instead.

Use the workspace's existing ID allocation procedure and transactions; detect collisions and deduplicate against siblings before creating. Write the real `product_id`, normative draft text, rationale/source from the existing parent and engineering evidence, acceptance criteria or an explicitly open criterion, `lifecycle_status=Draft`, `revision=1`, `parent_requirement_ids` containing exact existing parent ID(s), optional appropriate `traceability`, requirement revision snapshot where supported, and append-only audit with actual actor/time. Read back the saved record and link(s). Unknown limits, protocols, hardware details, ASIL, test outcomes or other design commitments are identified as **Open Decision**, never fabricated for a polished Draft.

A parent may have **zero or more** child requirements and a child may refine **multiple parents** when genuinely applicable; validate DAG, missing IDs, duplicates and cycles. Hierarchical parenthood means real normative refinement/flow-down only. `Depends On`, `Related To`, architecture links, Actor/Use Case associations and Test Case links belong in typed traceability, **not** in `parent_requirement_ids`. The original parent's approved revision and any frozen baseline remain untouched when children are created. Creating a Draft child is **not** silently adding it to a frozen baseline, declaring the parent delivered, or authorizing implementation beyond current task scope.

## Refine down to a useful atomic leaf — not arbitrary depth

For each proposed obligation ask whether it has a single independently assessable obligation, clear subject/system element, relevant triggering/operating conditions, observable outcome and realistic acceptance/verification method. Check clarity, necessity, feasibility, consistency, no conflicting sibling obligations and trace back to parent/need/use case. A single requirement may contain necessary conditions without violating atomicity. If a parent is already independently verifiable at its appropriate allocation level, do **not** force children just to produce a deeper tree. Stop when leaf obligations are independently verifiable and further division would merely restate implementation tasks, internal code steps, detailed test procedures or unconstrained design choices. No mandatory number of hierarchy levels or fixed physical-vs-software depth.

Where a parent spans different subsystems or concerns, derive appropriate independently verifiable children (for example external interface behavior, fault response, diagnostic/reporting) **only when those obligations follow from accepted context**. If a necessary constraint is not decided, draft an explicit conditional candidate and track the open decision; avoid new mandatory numerical thresholds. Do not infer a new safety requirement, ASIL, or safety approval. For safety-related items, apply project-approved ISO 26262 tailoring and designated safety review independently.

## Author–reviewer–approver separation

- **Writer / implementer / subagent:** may create and iterate Draft records and submit for review when allowed. Must never move a requirement that they authored/revised straight to `Approved` using their own authority, and cannot convert a test PASS, code merge, or lead task completion into requirement approval.
- **Reviewer:** a distinct accountable person or independently assigned agent checks the real requirement text and revision, necessary/atomic quality, parent intent and siblings, acceptance and verification approach, product applicability, interface/safety impacts, and completeness of links. `In Review` means under examination; negative feedback returns it to Draft or is recorded as Rejected with reason.
- **Approver:** the project-authorized accountable authority, often a product owner or explicitly delegated parent/lead agent within a **documented limited scope**. The lead agent does **not** inherit approval from being the lead or supervising the author. An upper agent may ask the user for a bounded delegation or collect a batch owner decision, then apply only decisions within that recorded delegation. A reviewer/approver must not be the same actor who wrote the specific revision under review; if separation is unavailable, leave `In Review` and obtain independent owner authorization. Always honor stronger project and safety/functional-safety independence rules.
- For each approval, record `requirement_id`, exact `revision`, decision, approver identity, authority source/delegation reference or verified owner decision, UTC timestamp and rationale/evidence in the **user's** `decisions`/audit system or mapped native ALM approval artifact. Read back. If the backend cannot capture independent approval proof, do not claim formal Approved status.

Lifecycle semantics: `Draft → In Review → Approved` only with the required review and real authority. `Rejected` is a reviewed candidate not accepted; `Superseded` refers to replacement by a different requirement, with successor trace, **not** an ordinary edit of the same ID; `Retired` is a formerly applicable obligation withdrawn by controlled decision. Normative text/criteria edits retain the same ID and create a new revision, with its new proposed state Draft until properly reviewed. Old exact revisions and frozen snapshots remain historical and immutable. Do not silently revive rejected requirements, edit approved text in place, or treat approval of a parent as approval of its children.

## Progressive delivery: draft early, review in batches

1. Resolve latest user-owned Guide, writer/task permission, exact parent revisions, affected frozen baseline, existing children and applicable standards profile.
2. Generate missing child Drafts and evidence-linked assumptions in a bounded batch while continuing unrelated authorized work. Do not create trivial duplicates or endless requirements for their own sake.
3. For each parent, show **covered obligations, derived Draft children, missing decisions and verification gaps**; distinguish structural coverage from actually verified or implemented behavior. Parent verification is not automatically satisfied by children.
4. Assign distinct reviewer/approver rights. If a real subagent exists, pass parent ID+revision, draft-writing permission and reviewer exclusions in its task packet; it may return Drafts, never self-approve. The parent lead reconciles concurrent edits and stale revisions before accepting results.
5. Group meaningful product/safety/interface decisions into occasional compact approval batches; don't ask permission for each Draft. If no authorized approver exists, keep candidates Draft or In Review and keep independent tasks moving.
6. Approved child requirements can be incorporated into a **new** candidate baseline only through the normal explicit baseline process. New children derived during implementation of an old frozen baseline belong to prospective scope until reviewed; do not retroactively rewrite that frozen deliverable.

Example (synthetic identifiers, not real project data): `CAN-REQ-010 rev 2 Approved` (communication recovery) may lead to `CAN-REQ-041 rev 1 Draft` (detect loss condition) and `CAN-REQ-042 rev 1 Draft` (observable recovery behavior), each with one parent. A separate timing number remains an undecided parameter until justified. A delegated reviewer can check the drafts; the author cannot approve them. The parent and any frozen snapshot stay exactly as they were.

## Quality and standards boundaries

Follow the project's configured editions of ISO/IEC/IEEE 29148, ISO/IEC/IEEE 15288 and, where applicable, Automotive SPICE / ISO 26262. These inform derivation, atomicity, allocation, bidirectional traceability, verification and independent safety review. They **do not** require universal fixed-depth decomposition, blanket artificial independence roles for every project, or authorization to automatically introduce implementation details. Do not claim formal certification or quote unverified proprietary clauses.
