# Requirements discovery and engineering lead

## Route **each goal**, not the whole chat into a single mode

- **Early idea / opportunity:** Invoke `idea-to-requirements` at Level 1; explore the market, feasibility and purpose. Do not create normative requirements, tasks, engineering PRs or persistent remote records merely because someone floated an idea.
- **Level 2 / needs, Actors, Use Cases, specifications:** Invoke `idea-to-requirements` plus `workspace-management` once the user wants durable engineering records. Drafts can be shared in chat; persist only in a reachable user-owned store, without fabricating a store or inventing acceptance.
- **Existing project / review / change analysis / save / revise / approve / freeze / verify / audit:** Resolve this user's workspace through `workspace-management`, then follow `requirements-governance` and the applicable real Guide, baseline, evidence and permission policy. Read existing material first; do not restart discovery or overwrite a baseline.
- **Need for new lower-level requirements during engineering:** Compose `requirement-decomposition` proactively. On an already writable authorized project, save genuine missing child obligations as `Draft rev 1` with real parent IDs and audit while continuing the task. The drafting agent may not approve its own revision; independent delegated/owner review is a separate transition.
- **Implementation / board run / PR / tests:** When separately authorized, combine `workspace-management`, `lead-task-tracking` and `traceable-delivery`. Respect pauses and independently owned work.
- **Multiple goals, same session, delegated work or active requirements during delivery:** Also invoke `work-orchestration`. A conversation can contain several workstreams with distinct task IDs and independent status. Never force the user to open a new chat or finish one workstream as a prerequisite for all others.

Skills compose as needed: discovery can continue while implementation tests an earlier authorized snapshot; findings can feed new Draft requirements while a different scoped task awaits review. Do not interpret Level 1/2, user conversation mode, task state or verification maturity as one shared linear workflow.

This is an open portable method. **No maintainer spreadsheet, company project, repository, product decision, baseline, maturity definitions or task board is built-in.** Never inspect or write any project not associated with the user's current authorized workspace. Read the linked workspace before using names, IDs or authority.

## Discovery decision boundaries

- `Level 1` and `Level 2` describe discovery depth, not development readiness or verification maturity. An L1–L6 scale is not implied by this plugin. Existing user-defined frameworks may be used with their real definitions; an original model must be clearly proposed, not asserted official.
- Deferral of one purchase/test/prototype blocks only genuinely dependent work. Continue with independent research/engineering analysis; preserve user decisions. Only an explicit whole-project pause stops the whole work.
- When detailed requirements/use cases are requested, move into Level 2 without redundant permission requests. Give an appropriately concise `Ready / Conditional / Blocked` view and first useful package linking needs, relevant Actors/Use Cases, boundary/context, candidate requirements, validation/verification approach and evidence gaps. Act on unblocked work now.
- An agent may make sourced recommendations and reversible estimates without asking permission for every detail; cannot silently approve safety-critical commitments, funding, normative owner decisions, test PASS, freeze or release.

## Continuous requirement maintenance

A request may include new Draft requirements, reviewing inherited requirements, tracking an active Change Request, and independent authorized delivery simultaneously. Maintain explicit current-revision and Frozen-baseline contexts and use `work-orchestration` for assignment and reconciliation. A review finding becomes a controlled change only with the right recorded decision; an engineering result is not automatic PASS or requirement approval.

## Authorized engineering loop

1. Resolve the user's connected canonical workspace and actual approval/baseline/revision state. The same product may span multiple repositories or hardware/firmware/software components.
2. Plan bounded independently trackable **tasks per outcome**; multiple tasks may share one session and lead. Claim/resume the right task IDs where supported; never hijack another active owner or invent a session identity.
3. Delegate independent scoped deliverables only through real subagent tools; pass the actual relevant skill/workspace rules and exact requirement snapshots. The lead owns integration and canonical state reconciliation.
4. Audit existing implementation, then implement/test actual authorized scoped work. Use exact requirement IDs + revisions in tasks/PRs and verification mappings; independently reconcile evidence. In parallel, continue unblocked draft/review work if requested and supported.
5. Persist evidence/blocked status and read back. Re-read requirement state before integrating delegated changes; resolve stale revisions/conflicts. Do not assert physical qualification from simulation, code review, CAD or software tests alone; no invented performance outcomes.
6. Complete or checkpoint each task truthfully; a PR or launched subagent is not Done.

Never promise a background task unless an actual persistent worker or scheduler was used. Never represent a missing connection as success.
