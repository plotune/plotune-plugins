# Importing an existing requirements workspace

1. Determine the **user-owned** source authority (RMS, Sheet, SQLite, CSV or existing task/ALM tool); obtain access from that user. Never use a maintainer workbook link or internal reference. Snapshot/backup the source first. Do not alter source during inspection.
2. Read actual tabs/entities, headers, formulas, validation and local governance policies. Map those fields to `schema/data-model.json`; common display-label aliases include `Requirement ID` → `requirement_id`, `Parent Requirement IDs` → `parent_requirement_ids`, `Hierarchy Level` → computed `hierarchy_level`, `From Type/ID` → `from_type`/`from_id`, and `Use Case ID` → `use_case_id`. Do not assume every sheet has identical columns or statuses.
3. Preserve stable IDs, exact requirement revision/text/criteria, real audit events, Actor and Use Case records, many-parent links and non-hierarchical typed traceability. Preserve baseline item snapshots and frozen states without rewriting older evidence. Do not manufacture historic `requirement_revisions` rows when only the latest text is available; record the completeness gap.
4. Treat computed columns (hierarchy depth, maturity/verification summaries, dashboards) as derived. An original workbook's formulas are **not** a portable normative rule. Recompute only from actual records, using any user-defined maturity mapping loaded from that workspace. Never import another organization's private maturity guide as a default.
5. Dry-run: report counts/IDs/revisions by table, duplicate IDs, orphan product/requirement references, invalid parent chains/cycles, broken typed links, mismatch between current requirements and exact frozen baseline snapshots, ambiguous statuses and nonportable links. Do not replace partial/missing values with invented approvals or PASS.
6. Build a new destination from blank template; migrate and validate readback, transactionally where supported; compare record counts and signed/exported checksums where feasible. The source remains authoritative until the user explicitly approves cutover. Changing the manifest to a new `canonical_backend` is a controlled switch, not simultaneous dual writing.
7. Store the new workspace binding in **user-owned** `requirements-workspace.json`; never ship their URL, credentials, product names or data as part of this plugin release.

For an established organization, respect its more restrictive governance rules and actual data model. Do not destructively reformat an existing sheet because it lacks a new template tab. Ask only the decisive questions needed for safe migration.

For existing in-place 1.0.0 workspaces adding persistent review/change tracking, see `docs/schema-upgrade.md`. This is different from backend migration or changing canonical ownership: do not rebuild populated user workbooks merely because the template now contains additional tabs.
